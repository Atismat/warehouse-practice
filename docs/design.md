# Проектные решения и границы проверки

Две реализации обслуживают одинаковые условные партии и заказы. В Python состояние представлено словарями; в Java данные скрыты в Cell, Lot и Order. Entity задаёт идентификатор и полиморфное представление snapshot, PlacementPolicy/AllocationPolicy отделяют best fit и FIFO от сервиса Warehouse. Копирование всех партий Python заменено в Java подготовкой общего плана до любых изменений: строки заказа имеют уникальный товар, поэтому их планы не пересекаются. Это верно для поставляемых BestFitPolicy/FifoPolicy. Внешние непроверенные стратегии не входят в контракт примера.

SQLite подходит для переносимой учебной БД без отдельного сервера. Все восемь логических сущностей сохранены. Вместо дублирования `used` и `reserved` они вычисляются представлениями. Это уменьшает число независимо изменяемых величин. Порядковые номера строк, резервов и движений сохраняют порядок снимка. Композитные FK запрещают резерв чужой партии или другого товара. Исторический план сохраняется после выдачи/отмены; активный резерв учитывает только RESERVED.

Сохранение — замена полного снимка внутри транзакции, не команда многопользовательского резервирования в SQL. SQLite выполняет проверки FK, CHECK, STRICT и триггеры вместимости. Баланс журнала, полнота плана и согласованность резервов дополнительно проверяются в приложении. Произвольные ручные SQL-изменения могут нарушить агрегатные инварианты; диагностические запросы нужны для их выявления. Java не подключается к SQLite.

## Реально обнаруженные ошибки

1. Исходный `receive(..., received_at=None)` передавал `None` в `datetime.fromisoformat`, возникал TypeError вместо ожидаемого предметного ValueError. Добавлена проверка строкового типа до изменений. Регрессия охватывает None, число, список и словарь.
2. При проверке общего UTC-набора Python 3.10 отклонял суффикс Z, а Java его принимала. Вход Z преобразуется в +00:00 до разбора; сохранённые даты и результаты сравниваются как UTC-моменты. Набор прошёл на Python 3.10.11 и 3.12.14.
3. При разработке SQL-ограничения тест даты без часового пояса обнаружил, что проверка последнего шестого символа принимала дефис даты за знак смещения. Добавлены минимальная длина и разделитель T; регрессия подтверждена. Полный календарный разбор остаётся в предметном коде.

## Качество

Логика предметной области отделена от файлового протокола и хранения. Резерв/выдача сначала проверяют весь заказ. В Java применены типы и закрытые поля; снимки предназначены для сериализации. Тесты содержат независимый ручной контроль 40+20 и 0/30/10; сравнение языков дополняет его. Сборка javac -Xlint:all не дала предупреждений. 40 успешных тестов подтверждают перечисленные сценарии, а не отсутствие любых ошибок. Измерений быстродействия, нагрузки и экономии нет.

## Предлагаемая команда и Scrum

Это модель будущей командной работы, а не описание состоявшихся встреч. Product Owner — представитель заказчика, определяет ценность и приоритеты; Scrum Master помогает применять Scrum и устранять препятствия; Developers отвечают за готовый инкремент. Внутри Developers нужны специализации аналитика складских процессов, Java/Python-разработчика и тестировщика с SQL. Один участник может совмещать специализации, но ответственность ролей должна быть понятна.

Приоритет P1: корректность FIFO, изоляция владельцев, атомарность заказа и сохранение. P2: журнал, автоматизация проверок и документация. P3: будущий интерфейс. Цель предлагаемого двухнедельного спринта — воспроизводимая выдача заказа с восстановлением снимка. Планирование определяет набор задач; ежедневная короткая синхронизация выявляет препятствия; обзор показывает контрольный сценарий; ретроспектива меняет способ работы. Критерии готовности: согласованное правило, код и схема, успешные сценарии отказа, инструкция запуска, проверяемый результат без секретов.

Для кладовщика нужны единицы измерения и безопасное размещение; для аналитика — моделирование процессов и данных; для разработчика — дискретная математика, алгоритмы, ООП, транзакции и Git; для тестировщика — граничный анализ, SQL и сверка журналов. Выбранное направление личного развития — backend-разработка складских систем, без заявления о достигнутой квалификации.
